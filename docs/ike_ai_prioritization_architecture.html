Technical & product design document

From a dynamic Eisenhower matrix to a student planning assistant

How Ike should use LLMs, deterministic constraints and, later, learned ranking to answer one question reliably: “What should I work on next?”

Audience Founders, engineering, ML, partners
Status Proposal for review
Reading time ~14 min
Scope Prioritization, planning, timetable, task generation

01Executive summary

The intuition behind an LLM-first design is right about the interface and wrong about the core. The LLM should be Ike’s reasoning and explanation layer, sitting inside a deterministic system that owns time, numbers and safety.

Decision 1

Use an LLM — as a bounded re-ranker

It reads structured features, re-ranks the top candidates, writes the “why”, and parses natural language. It does not compute dates, durations or availability.

Decision 2

No custom neural network yet

There is no behavioural data to train on. Ship the logging that makes a learned ranker possible in Phase 4, not before.

Decision 3

Two engines, not one

Prioritization ranks tasks; planning places them into free time. Planning is a constrained scheduling problem and needs a solver, not just a prompt.

Decision 4

Propose by default, automate by opt-in

Timetable-inferred tasks are suggestions. Users may enable auto-creation for high-confidence, whitelisted templates, always with undo.

Decision 5

Budget suggestions, don’t maximise them

Each event, day and course has a suggestion budget. Usefulness and historical acceptance gate what reaches the user.

Decision 6

Recommend, never control

Every recommendation can be accepted, snoozed, reordered, edited or questioned. Each of those actions is a labelled training signal.

02Problem framing

Students do not lack task lists. They lack a reliable answer to “given everything, what now?” — under deadlines, fixed timetables and limited energy.

Where Ike starts today

The current Ike engine (V0) is deterministic and already encodes useful structure:

  • current_urgency = min(10, initial_urgency + growth_rate × days)
  • priority_score = importance × current_urgency on a 0–100 scale, banded into low / medium / high / critical
  • current_effort = min(10, initial_effort + resistance × √days), with per-category resistance learned from completions
  • A 2D landscape (effort × priority) with quadrants and motivation-aware recommendations

This is a solid baseline and fallback. Its limits are what motivate the AI layer: urgency is a synthetic linear ramp rather than a real deadline, users must hand-score every task, there is no notion of available time, and nothing understands that “Finish ML coursework” and “Complete machine learning assignment” are the same thing.

The three questions Ike must answer

User questionProblem classOutput
“What should I work on right now?”Ranking with a top-1 decisionOne recommended task with a reason
“What are the 3 most important things today?”Ranking with a top-K decisionOrdered list with explanations
“I have 2 hours. What should I do?”Constrained selection (knapsack-like)A sequence that fits the window
“Plan my day around my timetable.”Scheduling under hard constraintsTime blocks avoiding calendar events
Key insight

Only the first two are pure ranking problems. The last two involve arithmetic over time, which LLMs do unreliably. That single observation drives most of the architecture below.

03Approaches compared

Three candidate engines, evaluated against Ike’s actual constraints: cold start, students’ messy natural language, and the need to be trusted.

Approach A

Rule-based

priority = f(deadline, importance, effort, …). Fast, free, reproducible, fully explainable. Brittle at the edges: it can’t read “reply to prof before Thursday’s meeting” or weigh competing soft goals, and every new nuance becomes another hand-tuned weight.

Approach B

Traditional ML

Learn P(do next), P(complete) or expected utility from behaviour (e.g. gradient-boosted learning-to-rank). Excellent once data exists and cheap at inference. Useless at launch, opaque to users, and liable to learn procrastination patterns as preferences.

Approach C

LLM-based

An LLM reads context and returns a ranking, reasons and a schedule. Strong zero-shot judgement and natural explanations. Weak at arithmetic and dates, non-deterministic, ordering-sensitive, costlier, and a privacy surface.

Evaluating the “LLM-first” intuition

LLM-first is correct for the interface: understanding free-text tasks, timetable semantics and explaining decisions. It is the wrong owner for the core decision mechanics, for four concrete reasons:

  1. Time arithmetic. “Due in 31 hours, needs 3h, only 4h free before then” must be computed, not inferred. A wrong deadline calculation is the single most damaging failure Ike can have.
  2. Ranking instability. LLM rankings shift with input order and phrasing. Students notice when the “top task” changes on refresh with nothing new.
  3. Unbounded cost and latency. Calling a model on every list render is unnecessary when most refreshes change nothing material.
  4. No learning path. An LLM alone does not get better from a user’s behaviour; a logged, feature-based pipeline does.
Verdict

Deterministic-first, LLM-in-the-loop. Deterministic code computes features, enforces constraints and produces a baseline ranking. The LLM re-ranks the top candidates within guardrails and explains. A learned ranker joins once behavioural data exists.

05Structured inputs and outputs

The LLM never sees a raw to-do list or raw calendar dump. It sees a typed, minimal context, and it must answer in a strict schema.

Why structure the input

  • Grounding. Stable task_ids let the validator check every claim against real records.
  • Pre-computed facts. Numeric features remove the arithmetic the model is worst at.
  • Token efficiency. Compact JSON is cheaper than prose, and the size is predictable.
  • Privacy. Only the fields needed for the decision are sent, so descriptions can be truncated or omitted.
  • Learnability. The same feature vector later trains the ranking model — one representation, two consumers.

Natural language still matters: the raw title is parsed once at capture time (LLM-assisted) into structured fields that the user can confirm, and is then stored as structure.

Guaranteeing predictable outputs

Use the provider’s structured outputs / JSON-schema mode so that malformed JSON is impossible, then validate semantics in the backend — a schema cannot know whether an id exists:

  1. Schema — enforced at generation time, then re-validated (Pydantic) on receipt.
  2. Referential integrity — every task_id and event_id must belong to this user and be active.
  3. Constraint checks — durations fit availability, schedule blocks do not overlap calendar events, at-risk tasks appear in top-K.
  4. Evidence check — each evidence key must exist in the supplied features, which discourages invented justifications.
  5. Stability check — if the top-1 differs from the last served answer without a material input change, keep the previous answer.
  6. Fallback — any failure serves the deterministic ranking, and the failure is logged.
Non-negotiable

The LLM proposes actions from a closed enum. The backend executes them through the same service functions a user action would use, with the same authorization checks. There is no path from model output to SQL. Destructive changes use archive_task (soft and reversible) rather than hard deletes.

06Timetable integration

Calendar data is the biggest context upgrade available to Ike. It turns “importance × urgency” into “what fits before the next lecture”. It must be normalized before any model sees it.

Normalized event representation

normalized_event.json
{
  "event_id": "evt_123",
  "provider": "university_timetable",
  "provider_event_ref": "hash:9f2c...",
  "type": "lecture",
  "course_id": "ML101",
  "title": "Machine Learning",
  "start": "2026-10-05T10:00:00+01:00",
  "end": "2026-10-05T12:00:00+01:00",
  "recurrence_group": "ML101-lec-weekly",
  "status": "confirmed",
  "busy": true,
  "classification": { "method": "rule", "confidence": 0.98 }
}

Normalization maps provider-specific shapes into Ike’s enum (lecture | tutorial | lab | exam | deadline | meeting | personal_busy | other), resolves the course via a per-user alias table (“ML”, “COMP70050”, “Machine Learning” map to ML101), converts everything to timezone-aware instants, and collapses recurrences. Personal events are reduced to personal_busy blocks with no title by default.

Provider abstraction

Do not assume

Timetable access varies by institution. Some publish ICS exports, some expose APIs, many offer neither. No specific university API should be assumed until verified. An ICS feed provider is the most portable first target because students can usually export or subscribe to their timetable, and Google and Outlook both expose read-only calendar scopes.

Permissions and data handling

Access

Least privilege

OAuth with read-only scopes where available. Per-calendar opt-in, so a student can share the timetable but not a personal calendar. Writing back to calendars is a separate, later permission.

Tokens

Encrypted, rotated, revocable

Refresh tokens are encrypted at rest with a KMS-managed key and never sent to the client or the LLM. Refresh happens server-side; a failed refresh marks the connection as degraded. Revoking access triggers provider revocation and data purge.

Minimization

Store normalized, not raw

Persist normalized events with a hashed provider reference. Raw payloads are processed in memory and discarded. Locations, attendees and descriptions are dropped unless a feature needs them.

Retention

Rolling window

Keep events from roughly −14 to +60 days, plus aggregate features such as weekly busy hours. Past events older than the window survive only as anonymised interaction features.

07Prioritization vs planning

Ranking answers “which task is most valuable next?”. Planning answers “when exactly?”. They share inputs but are different problems, and they need different engines.

Worked example — Monday, 08:00

08:00–10:00
Free 2h Plan ML assignment, part 1 (90 min focus + buffer)
10:00–12:00
Timetable ML lecture
12:00–14:00
Free 2h Plan Read statistics chapter (60 min) — this is the tutorial preparation, merged by dedup; lunch
14:00–16:00
Timetable Statistics tutorial
16:00–19:00
Free 3h Plan ML assignment, part 2 (90 min), then review ML lecture (30 min, suggested task)
Tue 23:59
Deadline ML assignment

Why not one component?

  • Different correctness criteria. A ranking can be “reasonable”; a schedule is either feasible or not (overlaps, overruns, missed deadlines).
  • Different algorithms. Planning is interval scheduling with deadlines and splittable jobs. A greedy earliest-deadline-first packer weighted by priority covers the MVP; a CP-SAT or ILP solver handles richer constraints later.
  • Different cadence. Rankings change when tasks change; plans change whenever the clock or the calendar moves. The planner reruns cheaply and often, without the LLM.
  • Debuggability. When a plan is wrong, you need to know whether the value judgement or the packing failed.

The LLM still adds value to planning: it supplies soft preferences as solver weights (“deep work in mornings”, “avoid starting a heavy task right before a lecture”) and explains the resulting plan.

08AI-generated tasks

With timetable access, Ike can notice tasks the student hasn’t written down. That is valuable and risky in equal measure. The task origin must be explicit everywhere.

origin = explicit

User-created

“Finish my ML assignment.” Authoritative. The AI may suggest edits (duration, deadline) but never rewrites or removes it on its own.

origin = suggested

AI-proposed

“Prepare questions for tomorrow’s ML tutorial.” Lives in a suggestions inbox and enters the task list only on accept.

origin = auto

Auto-created

“Review ML lecture” after every ML lecture. Only for templates the user enabled, above a confidence bar, labelled and undoable.

Product decision: A, B or C?

OptionUpsideDownside
A. Always confirmFull control, high trustFriction; weekly recurring tasks become chores to approve
B. Auto-create when confidentZero frictionModel confidence is not user intent; lists fill with tasks the student never chose and stops trusting
C. Hybrid (recommended)Suggest by default; per-template opt-in automationMore settings surface, mitigated with sensible defaults

Recommendation: C. Default to proposals. Offer “Automatically create high-confidence tasks from my timetable” as an explicit opt-in, scoped per template (“review after lectures: on; prepare tutorials: off”). Silent mass generation fails for reasons that go beyond accuracy:

  • Ownership. A to-do list is a commitment device. Tasks the student didn’t choose don’t feel like commitments, and ignored tasks erode the credibility of the whole list.
  • Noise compounds. At 30 timetable events per week, even a 20% unwanted rate adds six junk tasks weekly, and they also distort the rankings.
  • Feedback quality. An accept or dismiss on a suggestion is a clean label. Auto-created tasks that are silently ignored are ambiguous.
  • Reversibility. Even in auto mode, generated tasks carry their source, confidence and reason, and can be undone in one tap. Undoing teaches the gate to stop.

09Preventing task spam and duplicates

One lecture could “justify” eight tasks: read slides, review notes, flashcards, exercises, summary, questions… Generating them all would make Ike worse. Optimize for useful tasks, not for task count.

The usefulness gate

usefulness score (illustrative)
usefulness = (
    p_accept(user, template, course)    # Bayesian estimate, prior from all users
  * actionability(candidate)            # concrete verb, object and duration? else 0
  * relevance(candidate)                # boosted by explicit deadline, exam proximity, course weight
  * (1 - redundancy(candidate))         # overlap with existing and pending tasks
)

# Hard limits applied before scoring
MAX_PER_EVENT        = 1   # 2 for exams
MAX_PENDING_PER_DAY  = 5   # across all sources
MAX_PER_COURSE_WEEK  = 3
DISMISS_COOLDOWN     = "after 2 dismissals of a template, pause it for 14 days for that course"
Templates

Closed vocabulary per event type

A lecture maps to review_lecture or prepare_lecture, never both by default. Tutorial maps to prepare_tutorial, exam to a revision plan. Course-level rules can override (“no review tasks for Sport Science”).

Learning

Acceptance-weighted

p_accept is a Beta posterior per user × template, seeded from population rates. Three dismissals of “Make flashcards” and it stops appearing; consistent acceptance unlocks the auto-create option.

Actionability

No vague tasks

“Stay on top of Statistics” is rejected. A candidate needs a verb, an object, a duration of at most 2h, and a natural deadline (usually the next related event).

Digest

Batch, don’t ping

Suggestions are grouped into a daily digest (for example the evening before) instead of one notification per inference.

Deduplication cascade

“Finish ML coursework” and “Complete machine learning assignment” are the same task. Detect that cheaply first, and only escalate when ambiguous.

10Event-driven intelligence

Ike should think when something meaningful happens, not on a timer. Deterministic recomputation is cheap and runs on every event; LLM inference runs only when the outcome could change.

TriggerDeterministic work (always)LLM work (only if gated in)
Task created, edited or completedRecompute features, baseline rank, planRe-rank if top-3 baseline order changed
New lecture or tutorial in timetableTemplate inference, budget checkClassify only if the event type is ambiguous
Lecture endedInstantiate review_lecture if enabledNone
Deadline within 48h, or task becomes at-riskPin into top-K, recompute planRefresh explanation
Calendar change (moved or cancelled)Diff, re-plan affected blocks, archive orphaned auto tasksOnly if a high-priority block was displaced
User asks “What should I do now?”Fresh features for this moment and windowYes, with cache-first lookup on the context hash
Nightly jobTomorrow’s free windows, suggestion digestOne batched call per active user

“Material change” is defined deterministically: the baseline top-3 set changed, a task crossed into at-risk, available time today changed by more than 30 minutes, or the cached answer is older than its TTL (for example 4 hours). Everything else is served from cache. That is how event-triggered inference controls cost without making Ike feel stale.

Why not chatbot-first?

  • Decision fatigue is the problem. A chat box asks the student to formulate a query, which is another decision. A focus card answers before anyone asks.
  • Glanceability. The answer is needed in five seconds between lectures, not in a conversation.
  • Structured feedback. Buttons produce clean labels; chat produces free text that is hard to learn from.
  • Natural language still has a place — fast capture (“essay for Lee due Friday, ~4h”) and an optional “Ask Ike” for planning questions such as “I have 2 hours”, rendered as cards rather than paragraphs.

13Personalization and the feedback loop

Ike can personalize from day one without training anything, by turning behaviour into explicit features. Learned models arrive once the data justifies them.

Stages of personalization

Stage 1 · launch

Explicit context

Generic LLM plus stated preferences: working hours, focus-block length, course weights. No learning.

Stage 2 · weeks

Statistical profile

Per-user estimation bias per course, preferred hours, snooze patterns, template acceptance (Beta posteriors). Passed to the LLM as features.

Stage 3 · months

Learned ranker

Gradient-boosted learning-to-rank (e.g. LambdaMART) pooled across users, with user features. Later, user embeddings and contextual bandits for exploration.

The end state is LLM + user preference profile + learned ranking model + deterministic constraints: the ranker scores candidates, constraints filter them, and the LLM arbitrates close calls and explains. A pooled model with user features avoids needing large per-user datasets — a new student benefits from population patterns on day one.

Choosing the target variable

Candidate targetFailure mode if optimized alone
P(task completed)Pushes easy tasks; learns a quick-wins bias and rewards avoiding hard work
P(user follows recommendation)Tells users what they already wanted; reinforces procrastination
Time-to-completionPenalizes legitimately long tasks
User satisfaction (surveys)Sparse, delayed, noisy
Importance-weighted on-time completionRecommended primary target

Recommended: reward = followed × completed-before-deadline × importance, with a penalty when a high-importance task the system did not recommend becomes overdue. This measures whether the recommendation helped the student get important things done on time, which is Ike’s actual promise. Use follow-rate and satisfaction as guardrail metrics, not objectives.

system_prompt.txt — prioritization model
ROLE
You are Ike's prioritization reasoner for university students. You rank tasks
and explain the ranking. You do not chat, and you do not create tasks here.

OBJECTIVE
Maximize the chance that the student completes their most important work
before its deadline, given the time they actually have.

INPUT
A JSON object matching ContextSchema: now, user preferences, availability
windows, tasks with pre-computed features, upcoming events.
All times, durations and deadline distances are already computed.
Treat every numeric feature as ground truth. Never recompute dates or durations.

DECISION CRITERIA (in order of weight)
1. at_risk = true tasks: the free time before the deadline barely covers the work.
2. Consequence of delay: graded work, exams and external commitments outrank
   flexible personal tasks.
3. Importance and baseline_score: deviate from baseline_rank only with a reason.
4. Fit to the current availability window and the student's focus-block length.
5. Context switching: prefer work related to the next event when values are close.
6. Quick, important items (under 15 min) may be placed early if they unblock others.

HARD CONSTRAINTS
- Only reference task_ids present in the input. Never invent tasks, deadlines,
  courses or events.
- Every task with at_risk = true must appear in the top 3, or be listed in
  "uncertainties" with an explanation.
- recommended_duration_minutes must not exceed the current window or
  max_focus_block_min.
- Do not reorder tasks whose status is "done" or "blocked".

UNCERTAINTY
- If information is missing (no deadline, no estimate), say so in
  "uncertainties" and treat the task as flexible. Do not guess a deadline.
- If two tasks are effectively tied, keep the baseline order.

EXPLANATIONS

15Is this an AI agent?

Giving the LLM the ability to create tasks moves Ike along an autonomy spectrum. Being precise about where it sits clarifies the risks.

CategoryDefinitionIke stage
Text generatorProduces text; a human decides everythingExplanations only
RecommenderRanks options from a fixed setV1 AI prioritization
PlannerProposes multi-step sequences and schedulesV4 with solver validation
LLM with toolsEmits structured actions executed by the systemV3 task suggestions; auto-create when opted in
Autonomous agentPursues goals over time, chooses actions, acts without per-step approvalV5, partially, within strict scopes

Proposing a create_task action that a user confirms is tool use with a human in the loop, not agency. Auto-creation from enabled templates is bounded delegation: the user pre-authorized a narrow, reversible action class. Ike becomes agent-like only when it initiates multi-step behaviour on its own — re-planning a week, proactively messaging, rescheduling blocks. Even then, every action should stay reversible and scoped.

MVP autonomy level

Recommender plus proposed actions. The AI ranks, explains and suggests. It executes nothing without confirmation, except low-risk, reversible, per-template automations the student explicitly switched on. This maximizes usefulness and transparency while keeping autonomy risk low.

16Privacy and security

Schedules, grades-adjacent coursework and personal events are sensitive. Treat them as such architecturally, independent of any specific legal regime.

Minimize what leaves the system

Send the LLM pseudonymous ids, short titles, course codes and numeric features — no names, emails, locations or attendee lists. Personal events become anonymous busy blocks.

Provider data terms

Use API tiers with no training on inputs and with defined or zero data retention, where offered. Verify this per provider and region; it is a vendor-selection criterion.

Encryption and isolation

TLS everywhere, encryption at rest, OAuth tokens in a separate encrypted store, row-level security per user, and scoped service credentials for the AI worker.

User rights by design

Export, delete and disconnect flows that cascade to normalized events, embeddings and interaction logs. Prompts and outputs are logged with pseudonymous ids and short retention.

Prompt-injection surface

Event titles and task text are untrusted input (“Ignore previous instructions…”). The closed action enum, referential checks and the absence of DB access contain the blast radius.

Self-hosting path

The structured interface makes the model swappable. A small open-weights model can handle classification and dedup on own infrastructure, with frontier APIs reserved for ranking and explanations, or replaced entirely later.

Compliance obligations (e.g. GDPR for UK and EU students, institutional agreements) need proper legal review. This section identifies architectural levers, not legal conclusions.

17Evaluation framework

“The AI seems smart” is not evidence. Ike needs offline gates before shipping changes and online metrics after.

Offline

Ranking quality

NDCG@3 and Precision@K against user and expert orderings; Recall@K for at-risk tasks (target 100%); schedule feasibility rate; calibration of completion probabilities; ranking stability across input permutations.

Behavioural

Does it change behaviour?

Acceptance and completion rate of the top-1; snooze and dismiss rates; suggestion acceptance by template; time-to-completion; overdue-task reduction versus baseline.

Product

Does it matter?

Weekly retention, important tasks completed on time, self-reported decision fatigue (short periodic pulse), time from app open to starting a task.

Building the offline dataset before launch

  1. Scenario bank. 150–300 synthetic but realistic student weeks (tasks, timetable, deadlines), each with a ranking agreed by 2–3 reviewers. Include adversarial cases: missing deadlines, duplicates, injection-like titles, overloaded days.
  2. Invariant tests. Property checks that must always hold: no invented ids, at-risk tasks in top-3, no schedule overlaps, stable output under shuffled input order.
  3. Logged replay. Once live, every recommendation stores its context snapshot. New prompts or models are replayed against past contexts and scored against what users actually did (reorders, completions).
  4. Online A/B against the deterministic baseline, with importance-weighted on-time completion as the primary metric.
Most important comparison

Always keep the V0 deterministic ranker as a control arm. If the LLM cannot beat it on on-time completion of important tasks, it is only adding cost and latency.

Levers, in order of impact

  1. Gating — most renders never call a model.
  2. Caching on a context hash with a TTL; identical contexts are not re-asked.

  4. Model routing — small models for classification, dedup and parsing; larger models only for contested rankings.
  5. Batch APIs for nightly jobs.
  6. Prompt caching of the static system prompt where providers support it.

21Frontend platform: React Native, Expo and TypeScript

The plan is to launch on the web first, then ship to iOS. The frontend stack should make that a configuration step, not a rewrite.

Recommendation

Keep Ike’s current frontend stack: React Native with Expo and TypeScript, using Expo Router for navigation. Expo builds the same codebase for web (through React Native for Web), iOS and Android. The web launch and the later iOS release therefore share screens, business logic, API client and types.

Why this stack fits the AI architecture

TypeScript

Types end to end

The AI layer is built on strict schemas: context, recommendations and actions. FastAPI already publishes an OpenAPI spec, so the frontend can generate its types from it (e.g. openapi-typescript). If the backend changes the shape of a recommendation, the frontend fails at compile time, not on a student’s phone.

Reuse

No rewrite

Ike’s screens, task cards, sliders and auth flow already exist in Expo and TypeScript. Switching framework would spend months rebuilding V0 instead of building V1.

Web first

Fast iteration

A web build means prompt and ranking experiments reach users immediately, with no app-store review. That suits Phases 1–2, when the LLM layer changes weekly.

iOS next

A real native app

React Native renders native iOS components. EAS Build and Submit handle signing and TestFlight, and EAS Update can ship JavaScript fixes without a full store release (within Apple’s rules).

Caveats to plan for

  • Platform gaps. Some native modules (notifications, background tasks, device calendar) behave differently or are missing on web. Keep calendar sync and AI calls server-side so the web and iOS apps share one integration path.
  • Web feel. React Native for Web produces a solid app-like UI but not a content website. A marketing site, if needed, can be separate.

  • Native build stability. Pin the Expo SDK, and only add native dependencies with a clear need, to avoid the build failures already seen on Android.

23Recommended architecture for Ike

1 · Should we use an LLM?

Yes, as a bounded reasoning, re-ranking and explanation layer, and for natural-language capture and ambiguous timetable events. Not as the owner of time, numbers or writes.

2 · A neural network now?

No. No data, no labels, high MLOps cost. Build the logging now; train a pooled learning-to-rank model in Phase 4 and require it to beat the baseline offline.

3 · What does the LLM do?

Re-ranks the top baseline candidates using soft judgement (consequences, goals, context), writes grounded one-line reasons, proposes structured actions from a closed set, parses free text.

4 · What does deterministic code do?

Deadlines, free windows, workload feasibility, at-risk detection, dependencies, dedup steps 1–3, suggestion budgets, schedule packing, validation, fallback ranking and every database write.

5 · What data do we collect?

Exposures with feature snapshots, all interactions including reorders and snoozes, task lifecycles with estimate edits, and suggestion outcomes — versioned by model and prompt.

6 · How does it evolve?

V1 recommender, then timetable context, then human-confirmed suggestions, then a solver-backed planner with a learned ranker, then a bounded agent — each step gated by evaluation and user trust.

TL;DR architecture

Final recommendation

  1. Build deterministic-first, LLM-in-the-loop. Code owns time and truth; the LLM owns judgement and language.
  2. Separate prioritization from planning. Rank with LLM assistance; schedule with a solver.
  3. Suggest, don’t spam. Timetable-inferred tasks are budgeted, deduplicated proposals; auto-creation is opt-in, per template and undoable.
  4. Keep the student in control. A focus card, not a chatbot; every action reversible; every override a training label.
  5. Instrument from day one. The MVP’s most valuable long-term asset is its interaction log, not its prompt.
  6. One TypeScript codebase, web first. Keep React Native + Expo: launch on the web for fast iteration, then ship the same app to iOS.
  7. Earn autonomy. Move from recommender to planner to bounded agent only when evaluation beats the deterministic baseline on important tasks completed on time.
