Ike + IA : un LLM encadré par des règles

Comment Ike peut répondre de façon fiable à la question « Sur quoi dois-je travailler maintenant ? », en tenant compte des deadlines et de l’emploi du temps universitaire.

Format Digest, ~5 min de lecture
Statut Proposition à valider
Document complet Rapport technique (EN)

Le code calcule, le LLM raisonne et explique, l’étudiant décide.

Les règles gèrent tout ce qui doit être exact (dates, temps libre, faisabilité, écriture en base). Le LLM classe les meilleures options et explique pourquoi. Si sa réponse est invalide, Ike affiche le classement par règles : l’utilisateur a toujours une réponse.

01Le principe

Chaque recommandation passe par des règles avant le LLM et par une validation après.

02Qui fait quoi

Règles (code)

Ce qui doit être exact

Temps restant avant deadline, créneaux libres, charge vs capacité, tâches « à risque », dépendances, anti-doublons, plafonds de suggestions, toute écriture en base.

LLM

Ce qui demande du jugement

Reclasser les meilleures options, comprendre le texte libre (« dissert pour Prof. Martin, rendu après les vacances »), interpréter un cours ambigu, expliquer en une phrase.

Étudiant

Ce qui reste son choix

Accepter, reporter, réordonner, modifier, annuler. Chaque geste est un signal qui améliore Ike.

Garde-fou cléLe LLM ne touche jamais directement la base de données. Il ne peut proposer que 5 actions prédéfinies (créer, modifier, archiver, prioriser, planifier). Le backend les vérifie puis les exécute comme une action utilisateur.

03Pourquoi pas « tout LLM » ?

Risque si le LLM décide toutRéponse du modèle encadré
Erreurs de calcul sur les dates et duréesTout est pré-calculé par le code, le LLM ne recalcule rien
Classement instable (la tâche n°1 change sans raison)Score de base comme ancre, changement seulement si l’entrée a vraiment changé
Hallucinations (tâches ou deadlines inventées)Le LLM ne peut citer que des identifiants existants ; le reste est rejeté
Coût et latence à chaque ouverture de l’appAppel au LLM uniquement sur événement significatif, avec cache
Panne du fournisseurRepli automatique sur le classement par règles
Aucun apprentissageLes interactions sont enregistrées et nourrissent un futur modèle

Et un réseau de neurones maison ? Pas maintenant : sans données d’usage, il n’a rien pour apprendre. On collecte dès le MVP et on l’entraîne plus tard, à condition qu’il batte le classement par règles.

04Tâches générées depuis l’emploi du temps

Avec l’accès au calendrier, Ike peut proposer « Préparer le TD de stats de demain ». C’est utile, mais risqué si ça devient du spam.

Explicite

Créée par l’étudiant

Fait autorité. L’IA ne la modifie ni ne la supprime jamais seule.

Suggérée · par défaut

Proposée par l’IA

Arrive dans une boîte de suggestions et n’entre dans la liste qu’une fois acceptée.

Automatique · opt-in

Créée seule

Seulement pour les types que l’étudiant a activés (ex. « réviser après chaque cours »), avec un bouton Annuler.

Anti-spam

  • Plafonds : 1 suggestion max par cours, 5 par jour, 3 par matière et par semaine (valeurs de départ à ajuster).
  • Apprentissage : après 2 refus d’un type de suggestion, il est mis en pause ; un type souvent accepté peut passer en automatique.
  • Doublons : « Finir le projet ML » = « Terminer le devoir de machine learning ». On compare d’abord par règles et mots-clés, puis par similarité sémantique, et en dernier recours on demande à l’IA ou à l’utilisateur.

06Le MVP

Réalisable sur la stack actuelle (Expo, FastAPI, Supabase), sans modèle maison.

On livre

Dans le MVP

Vraies deadlines et estimations · moteur de règles · LLM qui reclasse le top 10 et explique · carte focus « Commencer / Pourquoi ? / Plus tard » · import ICS de l’emploi du temps · suggestions (sans auto-création) · journalisation complète.

On reporte

Plus tard

Création automatique · planification complète en blocs · connexion OAuth Google/Outlook · modèle entraîné · interface chatbot · écriture dans le calendrier.

L’actif le plus précieux du MVPCe n’est pas le prompt, c’est le journal des interactions : ce qui a été montré, dans quel ordre, et ce que l’étudiant a fait ensuite. Sans lui, impossible d’entraîner un modèle plus tard.

Ce qu’on mesure : part des tâches importantes terminées avant la deadline (indicateur principal), taux d’acceptation de la recommandation n°1, taux de refus des suggestions, rétention hebdomadaire. Le classement par règles sert toujours de groupe témoin : si le LLM ne fait pas mieux, il ne sert à rien.

07Frontend : React Native + Expo + TypeScript

Objectif : lancer d’abord sur le web, puis sur iOS, sans réécrire l’application.

Une base, deux plateformes

Web puis iOS

Expo compile le même code pour le web (via React Native for Web) et pour iOS. Le passage à iOS est une étape de build, pas une réécriture.

TypeScript

Cohérent avec l’IA

L’IA repose sur des schémas stricts. Les types du frontend sont générés depuis l’API FastAPI : si le format d’une recommandation change, l’erreur apparaît à la compilation, pas chez l’étudiant.

Déjà en place

Zéro réécriture

Les écrans, cartes, sliders et l’authentification d’Ike existent déjà en Expo + TypeScript. Changer de framework coûterait des mois sur la V0 au lieu de construire la V1.

Web d’abord

Expérimenter vite

Pas de validation App Store sur le web : les ajustements du LLM et du classement arrivent immédiatement chez les utilisateurs.

AlternativePourquoi on ne la retient pas
FlutterBon framework, mais réécriture complète dans un autre langage (Dart) et web moins mature
React web + CapacitorRapide sur le web, mais l’app iOS reste une page web dans une coque : expérience moins native
Next.js + app Swift séparéeQualité maximale, mais deux bases de code à maintenir : trop tôt pour notre taille
PWA seuleSuffisant pour un test, pas pour une vraie présence sur l’App Store
Points d’attentionCertaines fonctions natives (notifications, tâches en arrière-plan, calendrier de l’appareil) diffèrent sur le web : la synchro calendrier et les appels IA restent côté serveur. La sortie iOS demande un compte Apple Developer, une revue App Store et des déclarations de confidentialité pour les données de calendrier.

08Décisions à prendre en réunion

  1. Valider l’architecture « LLM encadré par des règles »

    Le code détient le temps et la vérité, le LLM le jugement et la langue.

    Recommandé : oui

  2. Stack frontend et ordre de lancement

    Garder React Native + Expo + TypeScript, lancer sur le web puis sur iOS ?

    Recommandé : oui, web d’abord, iOS une fois le produit validé

  3. Choisir à partir de quel repo travailler

    Repartir du repo Ike actuel, de celui de l’application de Sam, ou d’un nouveau repo commun ? Ce choix conditionne la stack, l’authentification, la base de données et l’organisation du travail à deux.

    À trancher avant le démarrage de la V1 ; il dépend aussi de la décision suivante

  4. Fusion d’Ike avec l’application de Sam

    L’application de Sam génère du matériel de révision à partir d’audio de cours (et bientôt de PDF). Ike pourrait transformer ce matériel en tâches priorisées (« Réviser la fiche du cours 3 avant le TD »). Quand fusionner ?

    • Avant la V1 : une seule app dès le départ et un seul socle (compte, base, design). En contrepartie, la date du 14 décembre devient plus risquée.
    • Après la V2 : chaque produit se valide seul. Il faut alors aligner dès maintenant ce qui facilitera la fusion : même stack, même fournisseur d’authentification, API compatibles.
    • Pas de fusion : deux apps indépendantes, éventuellement reliées par une intégration (import des fiches de révision dans Ike).
    À décider en réunion, idéalement en même temps que le choix du repo

  5. Niveau d’autonomie du MVP

    Recommandation + propositions, ou création automatique dès le départ ?

    Recommandé : recommandation + propositions, sans auto-création

  6. Première intégration calendrier

    Import ICS (le plus portable), Google/Outlook en OAuth lecture seule, ou un partenariat université ?

    Recommandé : ICS d’abord ; aucune API université n’est supposée sans vérification

  7. Choix du fournisseur LLM

    Critères : sorties JSON structurées, pas d’entraînement sur nos données, rétention limitée, coût, hébergement des données.

    À évaluer : courte comparaison de 2–3 fournisseurs

  8. Budget IA et règle de coût

    Suivre le nombre de tokens par utilisateur actif ; LLM appelé uniquement sur événement significatif.

    À fixer : plafond mensuel pour la phase pilote

  9. Confidentialité

    Minimiser les données envoyées au LLM (identifiants, titres courts, chiffres), événements personnels anonymisés, revue juridique (RGPD) avant tout accès calendrier.

    À planifier : revue avant la V2
